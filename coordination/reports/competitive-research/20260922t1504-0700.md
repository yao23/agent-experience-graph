## Material finding

This scan adds three commerce failure modes that are more specific than a generic “agent accessibility” score:

1. **Compatibility is a versioned relation, not merely a product attribute.** A retailer can expose highly structured compatibility data that conflicts with the manufacturer’s current compatibility matrix. Machine-readable data can therefore still be stale or wrong.
2. **Some commercial values are intentionally provisional until a later verification event.** A trade-in estimate is not a guaranteed realized credit; physical inspection can revise it after the consumer commits to the flow.
3. **A price label can have formal exclusions, and API discovery access can differ from transaction access.** Ticketmaster’s `All In Price` includes required fees but may exclude local taxes and selected delivery fees, while its Discovery API is broadly accessible with an API key and its purchase-capable Partner API is restricted to official distribution partners.

For H-COMMERCE, these patterns suggest that reusable Experience should not merely store facts. It should preserve **relation identity, commercial-value status, price-stage semantics, verification events, and access-tier boundaries** so that an agent knows when a fact can be reused and when it must be revalidated.

- `service/site`: Best Buy US + Apple Support
- `category`: consumer electronics / accessory compatibility
- `user_intent`: determine whether Apple Pencil (2nd generation) is compatible with iPad mini (A17 Pro), and identify compatibility-safe alternatives without relying on product-family assumptions.

### Accessibility observations

- `structured_data`: `SUPPORTED` (`OBSERVED/DECLARED`) — Best Buy product pages expose structured specification fields, and the official Products API documents structured pricing, availability, specifications, descriptions, and images.

- `browser_only`: `UNSUPPORTED` (`DECLARED`, catalog scope) — product/catalog data is available by API; this does not imply transaction capability is non-browser for a general consumer agent.

### Observable outcome

## Candidate 2 — Apple Trade In: estimated credit vs verified realized value

- `task_id`: `COM-20260922-APPLE-TRADEIN-001`
- `service/site`: Apple US
- `category`: electronics purchase / trade-in credit
- `user_intent`: determine what can be claimed about a trade-in credit before device inspection, and whether an agent may present an estimated trade-in value as a guaranteed effective purchase price.
- `constraints`: public/read-only; no serial number; no account; no device-specific personal information; no purchase/trade-in submission.
- `discovery_path`: Apple Trade In public FAQ -> Apple Trade In legal terms.

### Accessibility observations

- `structured_data`: `UNKNOWN` — this run did not verify public semantic product/quote JSON or a machine-readable trade-in quote interface.
- `api_available`: `UNKNOWN` — no public consumer trade-in quote API was established in this bounded scan.
- `auth_supported`: `NOT_APPLICABLE` for reading public program terms; device-specific quote/transaction auth was not tested.
- `transaction_supported`: `SUPPORTED` (`DECLARED`) — Apple describes online and store trade-in flows; no transaction was exercised.
- `verification_supported`: `SUPPORTED` (`DECLARED`, physical-inspection scope) — Apple/Vendor verifies device condition and can revise the original quoted value if inspection differs from the description or other conditions are not met.
- `browser_only`: `UNKNOWN`.
- `human_intervention_required`: `SUPPORTED` (`DECLARED`, exact-value realization scope) — an accurate device-specific value requires device identity/condition information and the realized value is subject to later inspection; this run intentionally supplied neither.

### Observable outcome

- `result`: `SUCCESS_READ_ONLY_PROVISIONAL_VALUE_BOUNDARY`.
- Apple states that in-store trade-in credit may differ from an online estimate if the device condition does not match what was described.
- For iPad, Mac, or Apple Watch, Apple says the serial number is needed to see an accurate trade-in value.
- Apple states that if a trade-in device’s verified condition differs, the original payment method may be charged the difference or a revised value may be offered; the consumer may reject a lower revised value in applicable flows.
- Apple’s legal terms explicitly state that trade eligibility and trade values are subject to vendor inspection and that quoted value can be revised for inspection mismatch, Find My status, or timing conditions.
- Therefore a consumer agent should not transform a headline/estimated trade-in credit into a guaranteed `net purchase price`. The correct fact state before inspection is `ESTIMATE/CONDITIONAL`, not `VERIFIED_REALIZED_VALUE`.
- `information_conflicts`: none required; the key distinction is value status across stages.
- `failure_point`: exact realized credit cannot be established without device-specific data and the later inspection event; intentionally outside scope.
- `human_intervention_point`: device identification/condition attestation and later acceptance/rejection of a revised value if applicable.
- `pages_consulted`: 2 primary public sources.
- `observed_at`: `2026-09-22T15:04:20-07:00`.

### Sources

- Apple Trade In: https://www.apple.com/shop/trade-in
- Apple Trade In legal terms: https://www.apple.com/legal/sales-support/trade-in/

### Experience candidate

`EXPERIENCE_CANDIDATE`: **provisional-commercial-value state** — preserve whether a credit/discount/rebate is `ADVERTISED | ESTIMATED | VERIFIED | REVISED | REALIZED`, what event advances the state, the validity window, and the conditions that can change the value. Never subtract an estimated credit from purchase price and present the result as guaranteed unless the relevant verification/eligibility conditions have been satisfied.

## Candidate 3 — Ticketmaster: All-In price semantics + discovery/transaction access split

- `task_id`: `COM-20260922-TM-ALLIN-001`
- `service/site`: Ticketmaster US
- `category`: live events / ticket shopping
- `user_intent`: determine what a publicly displayed ticket price includes and whether public event-discovery API access implies the ability to reserve or purchase tickets programmatically.
- `constraints`: public/read-only; no account/login; no seat reservation; no checkout; no API key creation; no payment.
- `discovery_path`: current event page -> Ticketmaster All In Price/help pages -> Ticketmaster Discovery API docs -> Ticketmaster Partner API docs.

### Accessibility observations

- `structured_data`: `SUPPORTED` (`OBSERVED/DECLARED`) — the event page exposes event/date/venue and min/max price information; the Discovery API exposes structured event data.
- `api_available`: `SUPPORTED` (`DECLARED`) — Discovery API is available with a developer API key for event discovery.
- `auth_supported`: `SUPPORTED` (`DECLARED`) — Discovery API requires an API key; Partner API also uses keys but is restricted to official distribution partners.
- `transaction_supported`: `SUPPORTED` (`DECLARED`, restricted partner scope) — Ticketmaster’s Partner API supports reserve/purchase/retrieve flows, but it is explicitly not an open API and requires an existing official distribution relationship. No inference is made that a general consumer agent has this entitlement.
- `verification_supported`: `UNKNOWN` for a general consumer-agent transaction; no order/receipt verification flow was exercised.
- `browser_only`: `UNSUPPORTED` (`DECLARED`, discovery and restricted-partner transaction scopes); ordinary public transaction access outside those scopes was not tested.
- `human_intervention_required`: `UNSUPPORTED` (`OBSERVED`, read-only task only); an actual consumer purchase may require account/payment/confirmation, which was not exercised.

### Observable outcome

- `result`: `SUCCESS_READ_ONLY_WITH_PRICE_STAGE_AND_ACCESS_TIER_BOUNDARIES`.
- A current Seattle Seahawks vs. San Francisco 49ers event page for 2026-10-11 exposed a minimum ticket price of USD 292 and maximum of USD 1,230, while also stating that tickets were not yet reserved and that JavaScript/cookies are required for certain purchase functions.
- Ticketmaster’s current help states that the `All In Price` includes required fees but local taxes and selected delivery fees may be added at checkout. Therefore `All In` is not necessarily identical to the final cash outlay in every transaction context.
- Ticketmaster’s Discovery API is broadly available after developer registration/API key issuance and supports search/look-up for events, attractions, venues, and classifications.
- Ticketmaster’s Partner API can reserve and purchase tickets but is explicitly restricted to companies with existing official distribution relationships.
- Therefore two invalid inferences must be avoided: `(a)` visible All-In price = guaranteed final total including every possible charge; `(b)` discovery API access = transaction authorization.
- `information_conflicts`: none; the key issue is scope/semantic precision rather than contradiction.
- `failure_point`: exact final total for a selected seat and public-agent transaction eligibility were intentionally not tested.
- `human_intervention_point`: none for read-only discovery; transaction-specific requirements remain outside scope.
- `pages_consulted`: 5 relevant public sources.
- `observed_at`: `2026-09-22T15:04:20-07:00`.

### Experience candidate

`EXPERIENCE_CANDIDATE`: **price-stage semantics + action-access tier** — attach a displayed price to an explicit stage and included/excluded components, and attach API capabilities to the access tier that grants them. A discovery-capable interface must not be treated as transaction-capable unless the current caller actually has the required transaction entitlement.

New **candidate-only / proposed** fields suggested by this scan:

- `relation_type`: e.g. `COMPATIBLE_WITH | REQUIRES | EXCLUDES`
- `relation_left_identity`
- `relation_right_identity`
- `relation_source_authority`
- `relation_observed_at`

- `verification_event`: e.g. `MANUFACTURER_MATRIX | PHYSICAL_INSPECTION | CHECKOUT | RECEIPT`
- `quote_valid_until`
- `price_stage`: `DISCOVERY | SELECTION | CHECKOUT | FINAL`
- `price_components_included`
- `price_components_excluded`

These extend, rather than replace, the previous proposed `source_surface`, `source_authority`, `entitlement_scope`, `conflict_state`, `commercial_fact_scope`, `freshness_class`, `observed_at`, and `evidence_kind` fields. ### Stronger experimental control recommendation

For any future H-COMMERCE execution, a simple `no guidance vs Experience` comparison may overstate AEG-specific value. Prefer, where budget permits, a three-arm design:

1. baseline task + current sources,
2. baseline + a short generic commerce-checklist of matched length/information budget,
3. baseline + independently produced, task-conditioned verified Experience.

The key question is whether verified Experience provides incremental value beyond a well-written static checklist, not merely whether an extra correct instruction helps.

## Decision

This run materially strengthens H-COMMERCE as a **state/scope/relation discipline** rather than a recommendation thesis. The most informative new result is the Best Buy/Apple compatibility conflict because it demonstrates that even structured retailer data can contain a wrong or stale relation that a current manufacturer oracle can falsify. Apple Trade In adds a distinct `estimate -> verification -> revised/realized` value lifecycle, while Ticketmaster adds explicit `price-stage` and `API-access-tier` semantics.

P7, P8, and P9 are all testable without login, payment, or personal data and have objective failure criteria. The strongest next test is P7 because its oracle is especially clean and the conflict is already present in current public evidence.

No transaction, login, payment, model experiment, queue mutation, ranking change, or new execution authorization was performed.
